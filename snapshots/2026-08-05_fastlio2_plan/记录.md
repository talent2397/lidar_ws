## 1. 问题现象

- `/merged_points` 点云经常穿透到 grid / 地面以下，运动时尤其严重（z_min 最深可达 -11.5 m）。
- 之前还观察到静止时 lidar1 的点云“很飘”。
- 原始点云 `/rslidar_points_1`、`/rslidar_points_2` 在各自雷达坐标系下是干净的（z_min ≈ 0.046~0.048 m），因此所有穿透都来自 TF 变换，不是雷达数据本身的问题。

## 2. 分析结论

### 2.1 静态外参偏差（已解决）

- 旧外参下，用 IMU 加速度计重力方向 + 点云地面拟合交叉验证：两个雷达相对 world 的倾斜约 11.2° / 12.5°，这就是静止时也穿透的原因。
- 用 20260804_160126 bag 的静止段（每雷达 80 帧，约 650 万点）拟合地面平面后，更新了 URDF 外参。
- 新外参在静止段验证：地面拟合 `z = -0.0058x + 0.0037y + 0.0033`，倾斜 0.39°，offset 3 mm，基本完美。

### 2.2 运动时穿透的真正原因（当前结论）

新 bag `dual_lidar_20260804_161906`（121 帧 merged，纯静态 TF）：

| 阶段 | 结果 |
|---|---|
| 静止段（前 30 s） | 地面在 z≈0，倾斜 0.39°；仅 0.04% 点 < -0.2 m |
| 运动段（30~60 s） | 8~16% 点 < -0.2 m，z_min 最深 -11.5 m；地面整体上移约 0.23 m（传感器被压低），一侧出现动态倾斜 |
| 停止后（60~73 s） | 陀螺归零（\|ω\|≈0.02）、\|a\|≈1g，但穿透未恢复：2~8% 点 < -0.2 m |

IMU 重力方向验证：运动前后两个 lidar 相对初始姿态**永久偏了 7.25° / 7.24°**，与点云残余倾斜吻合。

**结论：** 新静态标定本身是对的；剩余穿透是因为球滚动/悬挂回弹导致 lidar 相对 world 的姿态和高度在运动中变化，且运动结束后不回到原位。静态 TF 无法解决，必须用 lidar 内置 IMU 做动态补偿（把 lidar 的姿态实时变换到 world 下）。

## 3. 遇到的问题与解决方案

### 3.1 rosbag2 录制崩溃（SQLite error 1299）

- 现象：`ros2 bag record` 启动后立即崩溃，只留下 `.db3` 没有 `metadata.yaml`，报 `SQLite error (1299): constraint failed`。
- 原因：rosbag2 0.15.16 已知偶发 bug（[ros2/rosbag2#1971](https://github.com/ros2/rosbag2/issues/1971)）。
- 解决：
  - `record_bag.sh` 增加自动重试：失败后把残包移到 `bags/_broken/`，自动重录（最多 5 次）。
  - 残包保留在 `bags/_broken/`（未删除，但不可用于分析）。
  - 备选方案：`sudo apt install ros-humble-rosbag2-storage-mcap` 改用 mcap 存储（尚未启用）。

### 3.2 动态补偿旋转公式错误

- 现象：开启 suspension_compensator 后动态 TF 漂移到 170°。
- 原因：`rotate_vector_by_quat()` 符号错误，180° 旋转被算成恒等变换。
- 解决：重写四元数旋转公式，用 scipy 验证与标准实现一致。

### 3.3 静态外参偏差 11~12°

- 解决：自动地面平面标定 → 更新 URDF（见第 4 节数值）。

### 3.4 suspension_compensator 设计缺陷（本次修改）

原 v2 版本有三个问题：

1. **静止时把累计旋转归零**：对球式机器人是错的——球滚完后 lidar 不回到初始姿态，归零会删掉刚需要的补偿。
2. **只补偿旋转，不补偿 z 方向回弹**：运动时传感器被压低约 0.23 m。
3. **只用陀螺积分，没有用加速度计校正漂移**；静止检测只看角速度，垂直回弹测不到。

**v3 方案：**

- 取消“静止归零”，保留累计姿态；
- 静止时用加速度计重力方向做慢速漂移校正（互补滤波）；
- 增加 z 方向回弹补偿（泄漏双积分，可调参数，默认开启）；
- 陀螺零偏只在低运动时更新（收敛加快到 ~2.5s）；
- 校正方向经过离线仿真验证：`q_accum ⊗ q_corr⁻¹`（右乘共轭），直接右乘会把角度反向放大；
- 加速度计校正加 0.5° 死区，避免与静态标定的微小差异打架。

**v3 离线仿真结果**（用 161906 bag 的 IMU 数据回放）：

- 静止段：漂移约 1.2°（主要是加速度计无法观测的 yaw），z 补偿接近 0；
- 运动段：陀螺积分跟踪实际姿态（包含球体滚动产生的大角度 yaw）；
- 停止后：姿态与加速度计重力方向偏差在几秒内收敛到 ~0.6°，z 补偿回到 0 附近；
- 已知限制：yaw 方向漂移无法用加速度计校正（需要磁力计/点云特征，后续再做）；z 补偿对持续压缩（实测约 23cm）跟踪有限，只能部分补偿回弹振荡。

### 3.5 融合节点没有按点云到达时刻查 TF（v3 验证后新发现）

用 164735 bag（动态补偿开启）验证 v3 后，运动段穿透减半（%点<-0.2m 从 8.3% → 4.2%），
但未消除。离线分析发现：

- 穿透与动态 TF 摆动速度强相关：TF 旋转速率 <2°/s 时仅 0.03% 点穿透；
  10~100°/s 时升到 3.8~4.7%。
- 原因：当时的 `point_cloud_fusion.py`（后更名 `point_cloud_fusion_py.py`）用
  `rclpy.time.Time()`（处理瞬间的最新 TF）变换整帧点云；
  融合定时器 20Hz，动态 TF 摆动可达 50°/s，几十毫秒延迟就会让远距离点错位数米。
- 原始点云没有逐点时间戳字段（只有 x/y/z/intensity），无法做标准逐点去畸变。

**解决（fusion v2，离线验证）：** 融合时按每个点云的“到达时刻 - 50ms”回查 TF
（50ms 是离线扫参最优值，等价于扫描中点时刻）。离线重算 164735 bag：

| 指标（点<-0.2m 比例） | 原录制 | 到达时刻 TF |
|---|---|---|
| 全部帧 | 1.36% | 0.27% |
| 运动段 | 4.32% | 0.75% |
| 静止段 | 0.11% | 0.04% |

修改文件：`src/spherical_robot_description/scripts/point_cloud_fusion_py.py`
（当时文件名为 `point_cloud_fusion.py`；`tf_lookup_offset=0.05s`，可调）。

### 3.6 170307 bag 发现的新问题（fusion v3 + compensator 修正）

170307 bag（动态补偿 + fusion v2 实测）暴露三个问题：

1. **z 补偿启动饱和**：录制开始前 z_disp 已积到 -0.28m（应 ≈0），
   整个点云被压低约 30cm → 静止段 29% 点穿透。
   原因：z 零偏未初始化，启动瞬间 a_vert 偏移被积分到限幅。
   **修复**：首次进入 z 补偿时用当前 a_vert 初始化零偏；高通收敛加快到 ~5s；
   限幅收窄到 ±0.15m。
2. **融合输出骤减（144 → 32 帧）且 58s 后停摆**：
   同步检查用两雷达各自的 header 时间戳（内部时钟不同步，|差|<50ms 只有 49.6%）；
   tf2 过去时刻查询依赖缓冲历史。**修复（fusion v3）**：
   同步改用同一时钟的到达时刻；直接订阅 /tf 维护 2s 环形缓冲，
   按到达时刻-50ms 取最近变换；发布后记录已融合时刻避免重复帧
   （v3 阶段曾用“清空缓存”，3.9 起改为不清缓存）。
   离线重算：帧数 32 → 629。
3. **加速度计校正 10° 上限挡住大偏差**：本次录制静止时两雷达相对重力
   偏约 14°（164735 只有 1.1°，疑为测试地面不平或机器人被垫斜），
   14° > 10° 上限导致校正完全不生效，TF 保持标称姿态。
   **修复**：上限放宽到 30°，离线仿真 14° 偏差 5s 内收敛到 <0.7°。

> ⚠️ 注意：如果地面本身是斜面，平坦 grid 下点云必然“穿透”，
> 动态补偿只能保证雷达姿态与重力对齐，无法把斜面变平。验证时请用水平地面。

### 3.8 Python 融合节点性能瓶颈 → C++ 重写（173115 bag）

173115 bag（fusion v3 + 全部修复实测）：

- 静止段：0.06% 点<-0.2m，地面倾斜 0.32°/0.21° —— 已经干净；
- 运动段：2.35% 点<-0.2m（从 8.3% 降下来，但未达离线 0.09%）；
- 真机只有 173 帧/105s，而离线重算可以有 728 帧。

原因：rclpy 给 `PointCloud2.data` 赋值约 **163ns/字节**，160k 点（2.5MB）
要 ~400ms，Python 融合节点物理上达不到 10Hz；executor 饱和导致
使用旧 TF、丢失配对。

**解决**：融合节点重写为 C++（`src/point_cloud_fusion_node.cpp`，
可执行文件 `point_cloud_fusion`），单帧处理 <5ms；Python 版改名
`point_cloud_fusion_py.py` 留作参考。launch 已指向 C++ 版。

### 3.9 174604 bag：C++ 节点两个 bug 修复

174604 bag（C++ 版首次实测）：

- 静止段 0.03% 点<-0.2m；运动段 1.45%（继续下降）；但输出只有 1.4Hz。

发现 C++ 节点两个 bug：

1. **merged.width 写错**：设成 `t1.width + t2.width`（192），
   但数据包含两雷达全部行（172800 点），RViz/read_points 只会读 192 点；
   **修复**：`width = t1.height*t1.width + t2.height*t2.width`。
2. **发布后清空缓存丢配对**：新 raw1 与下一帧 raw2 配对常超 50ms，
   导致频率只有 1.4Hz；**修复**：不清缓存，记录已融合时刻，
   任一侧有新点云就重新配对；同步窗口放宽到 80ms；定时器 20ms。

预期修复后输出 ~7-9Hz（实际受 80ms 同步窗口限制，最终实测 ~4.4Hz，见 3.14）。

### 3.10 175142 bag：C++ 节点启动即崩溃（时间源不匹配）

175142 bag 中 `/merged_points` 完全没输出：C++ 节点启动后 ~0.6s
静默 SIGABRT（exit -6），launch 日志为空。

用节点自检（`FUSION_SELFTEST=1`）复现出异常：

```text
fuse exception: can't subtract times with different time sources [1 != 2]
```

**根因**：`last_fused1_/last_fused2_` 用默认构造的 `rclcpp::Time`
（时间源=RCL_ROS_TIME=2），与 `this->now()`（RCL_SYSTEM_TIME=1）相减
直接抛异常；异常从定时器回调冒泡 → std::terminate → SIGABRT。

**修复**：用 `this->now()` 初始化已融合时刻；同时给所有回调加 try/catch、
变换循环加越界保护、publisher QoS 改为 reliable（RViz 默认可靠订阅，
之前 best-effort 导致 RViz 收不到 /merged_points）。
自检已通过。

### 3.12 2026-08-05：180158 / 100408 bag 均 0 帧（诊断中）

**结论（已解决）**：状态日志显示节点其实在正常发布。0 帧根因是点云订阅 QoS：
